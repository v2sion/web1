감사 · 02가장 넓게 쓰임

캡션 색(#A6957D)이 힌트·프리셋 설명 전반에 반복 사용됩니다

"여러 개 골라도 돼요", "취준 · 첫 직장 · 흔들린 시기 · 지금" 같은 보조 설명 텍스트가 전부 이 색입니다. 크림 배경에서 2.66:1, 카드 배경에서 2.55:1 — 두 자리 모두 큰 텍스트 기준(3:1)도 못 넘습니다. 디자인 의도(보조 정보는 옅게)는 맞지만, 지금은 "옅다"가 아니라 "거의 안 읽힌다" 쪽에 가깝습니다.

수정 #A6957D → #7A6B54(크림 배경 4.74:1) 또는 #6E5F49(카드 배경 4.97:1). 같은 웜톤 브라운 계열 안에서 명도만 낮춘 값이라 무드는 유지됩니다.
감사 · 03경계선

치환 단어 강조(#C97F14)는 큰 텍스트 기준에서 근소하게 미달

질문 제목(20px)이라 "큰 텍스트" 3:1 기준이 적용되는데 2.94:1로 근소하게 못 넘습니다. 다만 이건 밑줄(#E8A33D)이 같이 있어서 순수 텍스트 대비 미달이 시각적으로는 완전히 죽지 않습니다 — 위 스와치에서도 밑줄 덕에 읽는 데는 지장이 없었습니다. 우선순위는 감사·01·02보다 낮습니다.

권고 급하지 않지만 여유가 되면 #C97F14 → #B36E0C 정도로 한 단계만 더 눌러도 3:1을 넘습니다. 필수 수정 목록에는 넣지 않았습니다.

02

폰트 — Song Myung은 굵기가 하나뿐입니다

브라우저의 document.fonts를 직접 순회해서 확인했습니다. Song Myung으로 로드된 모든 FontFace가 weight: 400, style: normal입니다 — 이 서체는 Google Fonts에 굵은 버전도 이탤릭도 없습니다.

폰트 · 01확인 필요

font-weight: 700 지정은 전부 브라우저 합성 볼드입니다

프리셋 이름("학창시절"), 버튼 텍스트("다음"), "AI가 정리한 글" 라벨 전부 700을 지정했지만 실제로는 브라우저가 강제로 획을 두껍게 그리는 합성(faux) 볼드입니다. 최신 Chrome/Safari 엔진에서 한글 세리프 합성 볼드는 대체로 봐줄 만하지만, 토스 인앱 WebView가 쓰는 렌더러(구형 Android WebView 포함)에서는 자소가 뭉개지거나 획이 불균등하게 두꺼워지는 경우가 실제로 있습니다.

확인 방법 실기기(특히 저사양 Android)에서 "학창시절" 프리셋 이름과 "다음" 버튼 텍스트를 확대해서 자소가 깨지지 않는지 확인. 문제가 보이면 굵기 차이 대신 색·크기로 위계를 만드는 대안이 이미 README에도 예비책으로 언급돼 있습니다.
폰트 · 02권고

이탤릭은 브리핑에 없던 추가 장식이고, 한글에서는 리스크만 있습니다

치환 단어("놀이터")에 font-style: italic이 붙어 있는데, 이탤릭 글리프가 없는 서체에 이탤릭을 걸면 브라우저가 글자를 기계적으로 기울이는 합성 오블리크를 적용합니다. 로마자는 원래 흘림체 전통이 있어 자연스럽지만, 한글 자소는 기울이도록 디자인되지 않아서 시각적으로 "찌그러진" 느낌이 날 수 있습니다. 색(#C97F14)과 밑줄만으로도 강조는 충분히 됩니다.

권고 font-style: italic 삭제. 색+밑줄 유지. 브리핑이 요구하지 않은 장식이라 빼도 방향성 손실이 없습니다.

공백 · 01최우선

최종 요약 화면이 없다는 게 가장 큰 공백입니다

브리핑 자체가 "이 앱의 완성감을 원한다"고 최종 화면에 가장 힘을 실어달라고 요청했는데, 정작 5개 예시 중에 빠졌습니다. 표지 이미지(4개 챕터 색 온도가 층층이 겹치는 연출), 최종 텍스트, 통계 3개, 하단 CTA — 지금 안의 톤을 그대로 이어받아 새로 짜야 하는 화면입니다.

공백 · 02색 미정의

알림 동의 카드는 지금 팔레트에 자리가 없습니다

기존 코드/목업은 이 카드를 amber(#E8A33D 계열)로 썼는데, 2a 안의 amber는 이미지 광원용 포인트로만 정의돼 있어서 "카드 배경"으로 쓰기엔 채도·용도가 다릅니다. 로즈(#B4649A/#F5E1EC)를 재사용할지, amber를 옅게 눌러 새 카드 배경을 만들지 결정이 필요합니다.

공백 · 03실무 영향

"+ 직접 쓰기" 입력 행이 빠지면 개발자가 임의로 채우게 됩니다

기능적으로 실제 코드에 이미 구현된 인터랙션(칩 목록 아래 인라인 입력+추가 버튼)인데, 이 안에는 등장하지 않습니다. 이대로 개발에 넘기면 개발자가 다른 요소(예: 온보딩 CTA)의 스타일을 임의로 가져다 쓰게 되고, 그게 이 안의 톤과 안 맞을 위험이 있습니다.

04

로직 갭 — 치환 강조는 디자인엔 있지만 코드엔 없습니다

이건 CSS 문제가 아닙니다. 실제 앱의 question.js를 확인한 결과, 지금은 stem()이 완성된 문장 전체를 문자열로 돌려주고 화면은 그걸 그대로 이스케이프해서 넣습니다 — "놀이터" 부분만 따로 감싸는 지점이 코드에 없습니다.

// 지금 코드 — src/screens/question.js
function renderQuestionText(text) {
  return esc(text); // 문장 전체를 그냥 이스케이프. "놀이터"만 따로 감쌀 지점이 없음
}

// questions.js의 stem()도 완성 문장을 통째로 반환
stem: (v) => v ? `${v}에서는 주로 뭘 했나요?` : '그 시절엔 주로 뭘 하며 보냈나요?'
구현 · 01코드 변경 필요

stem이 "치환 위치"를 같이 돌려주는 구조로 바꿔야 강조가 가능합니다

가장 적은 변경으로 되는 방법은 sentinel 마커입니다. stem()이 완성 문장 대신 {} 자리표시자가 있는 템플릿을 돌려주고, question.js가 그 자리만 <span class="fill">으로 감싸서 렌더링합니다.

// questions.js — 반환 형태 변경
stem: (v) => v
  ? { tpl: '{}에서는 주로 뭘 했나요?', fill: v }
  : { tpl: '그 시절엔 주로 뭘 하며 보냈나요?', fill: null }

// question.js — 렌더링부만 교체
function renderQuestionText(q) {
  if (!q.fill) return esc(q.tpl);
  const [before, after] = q.tpl.split('{}');
  return `${esc(before)}${esc(q.fill)}${esc(after)}`;
}
영향 범위 questions.js의 short·deep stem 정의 8개(챕터4 × 2)와 question.js의 renderQuestionText() 1개 함수만 바뀝니다. main.js의 resolveQuestionText()는 지금처럼 qDef.stem(value)를 호출해 결과 객체를 그대로 넘기기만 하면 됩니다 — 호출부는 무변경.

06

결정이 필요한 것

① 대비 수정 4건을 지금 바로 적용할까요?

색상값만 어둡게 눌러 재적용하는 작업이라 톤 손실이 거의 없습니다. 코드 반영 시 같이 넣으면 나중에 따로 QA 라운드를 돌 필요가 없습니다.

권고네 곳 모두 지금 적용. 위 섹션 01에 수정 hex 값을 이미 계산해뒀습니다.

② 미설계 화면 6개는 어떻게 할까요?

같은 Claude Design 세션에 이어서 요청할 수도 있고(가장 정확), 제가 이번 안의 토큰(색·타이포)만 뽑아서 코드 단계에서 나머지 화면에 직접 확장할 수도 있습니다(더 빠르지만 디자이너 검수 없이 진행).

권고최종 요약(공백·01)만 Claude Design에 추가 요청하고, 나머지 5개(홈·AI고지·알림카드·광고·직접쓰기 입력)는 기존 토큰을 그대로 확장해 코드 단계에서 채우기. 전부 다시 요청하면 리드타임이 늘어납니다.

③ 치환 강조 기능을 코드에 반영할까요?

섹션 04의 sentinel 마커 방식으로 구현 범위가 명확히 나옵니다. 이 기능이 없으면 2a 안의 시각적 핵심 장치 하나(치환 단어 강조)를 못 씁니다.

권고반영. 변경 범위가 작고(2개 파일), 검토 「기억을 꺼내는 순서」에서 이미 중요하다고 판단한 장치입니다.
