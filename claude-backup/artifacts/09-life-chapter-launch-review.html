판정

기술 설계는 한 군데를 크게 고쳐야 합니다. Supabase + Edge Function은 새 인프라입니다. 같은 일을 하는 검증된 스택이 핑계운세/개발/app/api/에 이미 돌아가고 있습니다 — GROQ 프록시 + Upstash Redis + 한국어 후처리 가드. 이걸 쓰면 개발 1~2일이 줄고 새 장애 표면이 0입니다.

수정 · 01 아키텍처

Supabase를 쓰지 마세요 — 같은 일을 하는 스택이 이미 운영 중입니다

PRD §11은 Supabase + Edge Function 프록시를 지정합니다. 그런데 핑계운세/개발/app/api/에 필요한 조각이 전부 이미 있고, 별핑계로 실서비스 검증까지 끝난 상태입니다.

  • fortune.js — GROQ 프록시. 키는 Vercel 환경변수, 클라이언트 노출 0. 인생 챕터의 "AI 호출은 반드시 서버 경유" 요구를 그대로 만족합니다.
  • _lib/redis.js — Upstash Redis. KST 일자 키(todayKeyKST)와 자정 만료(secondsUntilMidnightKST) 헬퍼까지 구현돼 있어, §6의 "anonKey 기준 일일 AI 호출 10회 제한"이 새로 짤 게 없습니다.
  • _lib/korean.js — stripReasoning · isUsableKorean · cleanToKorean. AI 출력 후처리 가드. 수정·05에서 다시 필요합니다.
  • .agents/skills/에 upstash-redis-js · upstash-ratelimit-js 스킬이 이미 설치돼 있습니다.

데이터 모델도 Postgres가 필요 없습니다. 인생 챕터의 저장 단위는 "anonKey 하나당 진행상태 문서 하나"(프리셋 · 챕터별 답변 · 챕터별 요약문 · 완료 플래그)라서 Redis Hash 또는 JSON 한 키로 끝납니다. 조인이 없습니다.

대체안 Vercel 서버리스 함수 + Upstash Redis. api/chapter-summary.js(챕터 요약 생성, 호출 상한 검사 후 GROQ 프록시) · api/final-summary.js · api/progress.js(진행상태 read/write) 셋이면 충분합니다. 지름신 대기실 개발 브리핑도 사흘 전에 같은 결론을 내렸습니다 — "Supabase 같은 새 외부 의존성을 들이지 말 것".

수정 · 02 존립 리스크

오픈이슈 ① anonKey — 답은 절반 나와 있고, 진짜 위험은 다른 데 있습니다

PRD가 "앱의 존립 문제"로 지목한 부분이 맞습니다. 다만 질문을 정확히 나눠야 합니다.

  • anonKey 자체는 안정적입니다. 백서에 "로그인 강제 없이 getAnonymousKey() 익명 식별만으로 운영 가능"이 첫 프로젝트 검증 결과로 남아 있습니다. 동일 기기 · 동일 토스 계정 기준입니다.
  • 위험한 건 클라이언트 저장소입니다. 2026-08-25 공지(52623) — SDK 3.x origin 변경 시 기존 localStorage 데이터에 접근하지 못할 수 있고 마이그레이션 API로 병합이 필요합니다. 별점이 이 이유로 _SDK3전환.md에 localStorage 키 목록을 따로 적어뒀습니다.
  • 기기 변경 승계는 anonKey로 불가능합니다. 이건 로그인 없이는 해결되지 않습니다.
설계 결정 서버(Redis)를 진실 원본으로, anonKey를 키로, 클라이언트 저장은 캐시로만 씁니다. 이러면 origin 변경으로 localStorage가 날아가도 답변은 살아남습니다 — PRD가 그린 최악의 시나리오가 구조적으로 막힙니다. 기기 변경 승계는 v1 범위에서 빼고, 온보딩에 한 줄로 고지합니다. 토스 로그인은 완주율 데이터를 본 뒤 판단합니다 (로그인 추가로 인한 이탈은 확실하고, 기기 변경은 저빈도).

수정 · 03 품질 게이트

오픈이슈 ② AI 요약 품질 — 게이트는 맞지만 합격 기준이 없습니다

"착수 전 프롬프트를 여러 번 테스트해서 공유하고 싶은 수준인지 확인"은 옳은 판단인데, 이대로면 판정이 주관적으로 흐르고 결국 "일단 만들면서 고치자"로 넘어갑니다. 백서 B2의 교훈이 정확히 이 지점입니다 — "완료" 판정은 실제 산출물을 확인한 뒤에만.

별핑계에서 GROQ를 쓰면서 배운 것도 있습니다. qwen3.6은 리즈닝 모델이라 reasoning_effort를 끄지 않으면 영어 사고 과정이 본문에 그대로 노출됩니다. 병맛 핑계는 톤이 무너져도 웃고 넘어가지만, 자기서사는 톤이 한 번 어긋나면 그 사용자를 영구히 잃습니다. 모델 선택을 별핑계와 같이 두지 말고 다시 고르세요 — 1인당 호출이 5회뿐이라 상위 모델을 써도 비용이 감당됩니다.

합격 기준 프리셋 4종 × 답변 유형 3종(부실 = 대부분 건너뛰고 한두 단어 / 보통 / 성실 = 문항당 60자 이상) = 샘플 12개를 실제로 생성하고, 사람이 각각에 "이걸 카톡에 공유할 것인가 Y/N"으로 판정합니다. 9개 이상 Y가 아니면 착수하지 않습니다. 이 테스트는 코드 없이 API 콘솔만으로 가능하므로 지금 바로 시작할 수 있습니다.

수정 · 04 검수 리스크

정책 판정 §14가 낙관적입니다 — 민감 주제는 질문이 아니라 답변에서 들어옵니다

PRD §7은 질문 풀에서 죽음 · 질병 · 이별을 배제했고, §14는 그걸 근거로 "민감 콘텐츠 해당 없음 예상"으로 판정했습니다. 이 논리에 구멍이 있습니다. AI 요약의 재료는 질문이 아니라 사용자 답변입니다. "그 시절 가장 고마웠던 사람은?"에 사별한 가족을 쓰는 사용자는 반드시 나오고, 요약문은 그걸 그대로 서술합니다.

여기에 2026-08-19 공지(52485)가 겹칩니다 — 재난 · 죽음 · 질병 등 민감 주제 검수 기준 강화, 기존 출시 앱에도 소급 적용, 민감 주제를 다루는 서비스는 검수에 최대 1주일. PRD §15의 3주차 출시 일정에는 이 버퍼가 0입니다.

필요 조치 3건 ① AI 시스템 프롬프트에 "사별 · 투병 · 이별이 답변에 등장하면 사실만 담담히 다루고 극적으로 서술하지 않는다" 지침 명시  ② 요약 출력 후처리 가드 — korean.js의 isUsableKorean 패턴을 확장해 금칙 표현 검사 후 실패 시 재생성(이 재시도는 사용자 호출 상한 5회에 포함하지 않음)  ③ 콘솔 상세설명 · 스크린샷은 "회고 · 추억" 톤만 노출, "인생 정리"처럼 읽힐 문구 배제

수정 · 05 구조

화면 5개는 vanilla 단일 파일의 재검토 임계점입니다

백서 부록의 결론이 "화면 3개에선 프레임워크 없는 단일 파일이 오히려 빨랐다. 화면 5개 이상이면 재검토." 인생 챕터는 정확히 5개인 데다, 상태 복원 로직(어느 프리셋 · 몇 번째 챕터 · 몇 번째 질문 · 요약 생성 완료 여부)이 기존 앱 중 가장 복잡합니다.

그리고 이미 대가를 치르고 있습니다. 루트 CLAUDE.md에 "main.js 한 번 읽으면 200k 컨텍스트의 15%가 날아간다"는 경고가 있고, 무더위 체감 랭킹 94KB · 별점 75KB가 그 결과입니다. 단일 파일을 6번째 앱에서 또 선택하면 같은 비용을 또 냅니다.

권고 vanilla + ES 모듈 분할로 시작합니다 — main.js(부트 · 라우팅)와 화면별 모듈 5개, 상태는 단일 스토어 모듈. React + toss-miniapp-ui 도입은 권하지 않습니다: 그 라이브러리를 실제 앱에 붙여본 적이 한 번도 없어서, 신규 앱의 첫 시도로 삼기엔 리스크가 겹칩니다.

수정 · 06 푸시

푸시 §10 — 주간 리마인드는 빼고, 템플릿은 MCP로 만들지 마세요

PRD가 스스로 "별도 목적 동의 필요"라고 적은 주간 리마인드는 순수 리텐션 목적이라 광고성에 가깝고, 광고성 스마트발송은 10/1에 종료됩니다. v1.1 목록에서 삭제하고 기능성 2종(이어할까요 / 요약 완성)만 유지하는 게 안전합니다. 이 둘은 "사용자가 시작한 작업의 진행 상태 안내"라 허용 범주로 설계한 PRD의 판단이 맞습니다.

더 중요한 함정이 하나 있습니다. 기능성 푸시 템플릿을 콘솔 MCP(push_template_create)로 만들면 enabled:false 상태로 고착돼, 앱에서 알림 동의 팝업을 띄워도 아무 반응이 없습니다. 이 증상은 이미 한 번 겪었습니다 — 라이브에서 수 주간 방치됐습니다.

규칙 기능성 푸시 템플릿은 반드시 콘솔 웹에서 직접 등록합니다. 그리고 mTLS 인증서는 아직 어느 앱도 발급받은 이력이 없으니(백서 시점 미착수 → 지름신 브리핑에도 Day 1 할 일로만 남아 있음) 발급 리드타임을 먼저 확인한 뒤 일정을 확정하세요. PRD가 mTLS를 1일차 선행으로 잡은 판단 자체는 정확합니다.

03

그대로 두어야 할 것

4건

고치지 마세요. 기존 앱들이 뒤늦게 배운 것을 PRD가 선제적으로 반영한 부분입니다.

유지 · 01유지

AI 호출 상한 5회를 서버에서 강제 + 요약 DB 저장 후 재사용

기존 6개 앱 어디에도 이 수준의 비용 상한 설계가 없습니다. "재진입 시 재생성하지 않고 저장본을 읽는다"는 결정이 특히 중요합니다 — 재생성을 허용하면 사용자가 마음에 들 때까지 돌리면서 비용이 선형으로 늘고, 동시에 "내 이야기"라는 서사 자산의 고유성도 사라집니다.

유지 · 02유지

로그 스펙을 개발 지시문(§16)에 통째로 박아넣은 것

백서가 "Analytics 계측을 처음부터 넣기"를 Day 1 항목으로 못 박았는데, 실제로 이렇게 이벤트명·파라미터까지 확정해서 지시문에 넣은 건 이 PRD가 처음입니다. "답변 원문은 로그에 절대 넣지 말고 길이만"이라는 제약도 정확합니다.

유지 · 03유지

이정표를 "보상"이 아니라 "이탈 지점"으로 설계한 관점

§4-2의 "사용자는 어디서든 이탈하지만, 이정표가 있으면 이탈이 챕터 경계에 모인다"가 이 앱의 진짜 발명입니다. 이탈을 막으려는 게 아니라 이탈 위치를 예측 가능하게 만들어 푸시 명분을 확보한다는 구조 — 웨비나 사례에서 전환을 9%→14%로 올린 "대기 구간 + 기능성 푸시"와 같은 원리입니다.

유지 · 04유지

챕터1→챕터2 전환율을 단일 생사 지표로 잡은 것

§17의 "이게 낮으면 이정표 구조가 작동하지 않는다는 뜻이고, 다른 어떤 개선도 소용없다"는 판단이 맞습니다. 이 지표 하나를 core_metric의 대표 전환 지표로 등록하고, 나머지는 보조로 두세요.

결정이 필요한 것

3건

아래 셋은 제 판단으로 정할 수 없습니다. 답이 나오면 PRD를 기획 브리핑으로 승격시키고 5트랙 폴더를 만들겠습니다.

① 지름신 대기실과 인생 챕터 중 무엇을 먼저 냅니까?

둘 다 브리핑 단계이고 코드는 없습니다. 병행은 캐파상 불가능합니다.

권고지름신 대기실 먼저. 인생 챕터는 코드 없는 선행 3건만 병행.

② 인생 챕터의 사용자 식별을 anonKey로만 갑니까?

서버를 진실 원본으로 두면 데이터 유실은 막히지만, 기기 변경 승계는 여전히 불가능합니다. 토스 로그인을 넣으면 승계는 되지만 온보딩 이탈이 확실히 오릅니다.

권고v1은 anonKey + 온보딩 고지. 완주율 데이터를 본 뒤 재판단.

③ Supabase를 폐기하고 기존 스택(Vercel + Upstash Redis + GROQ 프록시)으로 갑니까?

PRD §11·§16이 Supabase Edge Function을 전제로 쓰여 있어, 승인되면 그 두 절을 다시 씁니다.
